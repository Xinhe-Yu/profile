Partie I : Contexte et Objectifs

    • - Bob débordé, process manuel

  • Objectifs
    • - automatiser, fiabiliser, et faciliter la contribution

Partie II : Aperçu du workflow CI/CD

  • Déclencheurs :
    • push sur main
    • pull_request vers main
    • workflow_dispatch pour déclenchement manuel
  • Étapes principales du pipeline :
    • Tests (backend & frontend)
    • Analyse qualité (SonarCloud)
    • Build Docker + Push vers Docker Hub

  • ⚠️ Build & push Docker seulement après merge sur main

Étape 1 : Tests automatiques

  • Backend :
    • Tests avec JUnit
    • Couverture avec JaCoCo
  • Frontend :
    • Tests avec Karma (Angular)
    • Couverture générée avec Karma coverage

  • 📄 Rapports publiés sur GitHub Pages (via peaceiris/actions-gh-pages@v4)
  • 🔁 Stockage des rapports pour analyse qualité plus tard

Étape 2 : Analyse qualité (SonarCloud)

  • Analyse séparée backend et frontend
  • Utilisation des rapports de couverture (tests précédents)
  • Contrôle de qualité basé sur :
    • - Sécurité
    • - Maintenabilité
    • - Bugs critiques ou duplications ? → PR bloquée

  • 🚦 Quality Gate = Feu vert/rouge sur la qualité du code

Étape 3 : Build et Docker Hub

  • Backend et Frontend buildés séparément
  • Authentification Docker dans GitHub Actions
  • Images créées avec docker build
  • Push automatique vers Docker Hub
  • Conditions :
    • - Tests passés
    • - Analyse Sonar validée
    • - Action déclenchée par un push sur main

  • 💡 Possibilité future : déploiement auto sur serveur via SSH

Quality Gates & KPI

🟢 Quality Gate : système de validation automatique

Indicateur Seuil Pourquoi c’est important
Couverture du nouveau code ≥ 80% Pour s’assurer que chaque nouvelle fonctionnalité est bien testée
New Blocker Issues = 0 Zéro bug critique introduit, on veut pas casser le site
Duplication (new code) ≤ 3% Évite le copier-coller et garde le code propre et facile à maintenir

Partie IV : Retours utilisateurs

  • "Impossible de poster une suggestion de blague, le bouton tourne et fait planter mon navigateur" → manque de tests backend + gestion d’erreur + tests E2E
  • "J’ai remonté un bug sur le post de vidéo il y a deux semaines et il est encore présent" → pas de tests de non-régression + pas de suivi clair des bugs
  • "Ça fait une semaine que je ne reçois plus rien, j’ai envoyé un email il y a 5 jours mais toujours pas de nouvelles…" → manque de logs/monitoring ou simple malentendu ➜ besoin de messages explicites

💡 Objectif : rendre l’app plus robuste, compréhensible et transparente pour les utilisateurs (et les contributeurs)

Pistes d’amélioration

  • 1. Renforcer la robustesse fonctionnelle
    • - Couverture backend trop faible (38%) ➜ viser les 80%
    • - Ajouter des tests end-to-end (envoi de blague, affichage...)
  • 2. Améliorer la gestion des retours utilisateurs
    • - Utiliser les issues GitHub pour suivre les bugs
  • 3. Suivre les indicateurs qualité
    • - Corriger les bugs critiques détectés par SonarCloud
    • - Valider régulièrement les security hotspots
  • 4. Renforcer l’architecture et la stabilité
    • - Ajouter des messages d’erreur ou d’état explicites dans l’UI
    • - Ajouter des logs ou alertes côté backend
    • - Gérer les environnements (dev, test, prod) avec des configs propres

Conclusion

  • - Une pipeline CI/CD opérationnelle et automatisée
  • - Qualité du code analysée à chaque PR
  • - Images Docker prêtes à l’emploi
  • - Et une roadmap claire pour fiabiliser l’app côté utilisateurs

    • 🚀 Prochaine étape : améliorer la couverture backend, ajouter les tests E2E, suivre les retours utilisateurs, et peut-être... accueillir de nouveaux contributeurs
