Partie I : Plan de test

  • Objectif : Vérifier le bon fonctionnement des principales fonctionnalités de l'application à l'aide de scénarios BDD
  • Méthodologie : Tests fonctionnels basés sur des scénarios Given / When / Then en langage naturel, facilitant la collaboration entre développeurs, QA et parties prenantes.

Plan de test - Authentification

  • Fonctionnalités testées
    • - Connexion avec identifiants valides / invalides
    • - Connexion via Google
    • - Validation des contraintes de mot de passe à la création de compte
  • Objectif : garantir que seules les identifiants valides permettent l'accès et que les erreurs sont correctement gérées.

Plan de test - Catalogue produit

  • Fonctionnalités testées
    • - Affichage des produits après authentification
    • - Recherche par nom
    • - Filtres par type de produit
  • Objectif : vérifier que les utilisateurs accèdent facilement à l’offre produit grâce à une navigation fluide et pertinente.

Plan de test - Simulateur AR

  • Fonctionnalités testées
    • - Chargement automatique du simulateur depuis la fiche produit
    • - Affichage du modèle 3D dans l’espace
    • - Contrôles de placement et retour au catalogue
  • Objectif : garantir une expérience AR fluide, intuitive et fiable

Plan de test - Tunnel d’achat

  • Fonctionnalités testées
    • - Ajout au panier depuis le simulateur
    • - Affichage du panier et du récapitulatif
    • - Validation du panier
    • - Paiement avec données valides et invalides (test sandbox)
  • Objectif : s’assurer que le processus d’achat est fonctionnel et réactif, y compris en cas d’erreur.

Fonctionnalités exclues des tests

  • Hors du périmètre fonctionnel
    • - Rendu visuel 3D (géré par bibliothèque externe)
    • - Paiements en production (test uniquement en sandbox)
    • - Performance (nécessite tests de charge spécifiques)

Partie II : Plan de sécurité

  • Objectif : Identifier les risques majeurs liés à l’application et proposer des solutions concrètes pour s’en prémunir.
  • Méthodologie : Évaluation basée sur le contexte de la v1, l’architecture technique, et les fonctions critiques de la v2.

Risque : Panne du serveur unique

  • Contexte : L’application repose sur une architecture centralisée. Un seul point de défaillance compromet l’accès complet.
  • Gravité : 5/5
  • Solutions : Infrastructure cloud multi-instances, load balancer, monitoring avec alertes.

Risque : Transmission de données non sécurisée

  • Contexte : Des APIs utilisent encore HTTP. Données exposées aux attaques man-in-the-middle.
  • Gravité : 4/5
  • Solutions : Passage intégral à HTTPS, certificats SSL/TLS auto-renouvelés, tests automatisés de sécurité réseau.

Risque : Stockage de mots de passe avec MD5

  • Contexte : MD5 est obsolète, vulnérable aux attaques par dictionnaire et rainbow tables.
  • Gravité : 4/5
  • Solutions : Bcrypt ou Argon2, politique de mot de passe fort, verrouillage après tentatives échouées.

Risque : Absence de tests automatisés

  • Contexte : Pas de tests dans la v1, risques élevés de régressions non détectées.
  • Gravité : 4/5
  • Solutions : Adoption TDD ou BDD, tests automatisés intégrés dans CI/CD, couverture progressive.

Risque : Injection SQL

  • Contexte : Zones de saisie utilisateur non protégées, risques d’attaques SQL sur login, recherche, etc.
  • Gravité : 3/5
  • Solutions : Utilisation d’ORM, requêtes préparées, validation côté client et serveur.

Partie III : Plan de sauvegarde des données

  • Objectif : Assurer la résilience de l’application et la restauration rapide des données en cas d’incident critique.
  • Exigences : sauvegardes quotidiennes, réplication hors site, RTO < 1h, RPO < 24h, tests mensuels, images système hebdo.

Données structurées (bases)

  • Technologie : Bases managées type PostgreSQL (AWS RDS, GCP Cloud SQL)
  • Garanties : snapshots journaliers, restauration à un point dans le temps, chiffrement au repos, audit log

Données statiques (fichiers, images, modèles 3D)

  • Technologie : Buckets cloud (ex : AWS S3, GCP Cloud Storage)
  • Garanties : versioning, export régulier, réplication entre régions

Résilience & haute disponibilité

  • Solutions : réplication inter-régionale, redondance active, infrastructure scalable avec load balancing
  • Objectif : éviter tout point de défaillance, maintenir le service même en cas de panne locale

Suivi & tests de sauvegarde

  • Monitoring : outils cloud (CloudWatch, Stackdriver, Datadog)
  • Tests : restaurations mensuelles en staging, vérification d’intégrité, alertes automatisées

Plan de restauration

  • Étapes : alerte → analyse → choix du snapshot → nouvelle instance → vérification → restauration → redirection du trafic → rapport post-incident
  • Entraînement : ce plan est utilisé aussi pour les exercices mensuels de restauration
